# 自定义打码接口规范

「自定义接口」渠道会按本规范调用你提供的打码服务。只要按下面的格式接收请求、返回结果即可，服务内部如何识别、是否限流或排队等，均不作要求。

## 1. 请求

```http
GET {接口地址}?gt=<gt>&challenge=<challenge> HTTP/1.1
X-API-Key: <API Key>
```

| 项 | 说明 |
|---|---|
| 接口地址 | 用户在客户端中填写的完整地址，路径不限，客户端不会自动追加路径 |
| `gt` | 极验验证码参数，客户端原样传入 |
| `challenge` | 极验验证码参数，客户端原样传入 |
| `X-API-Key` | 选填。用户在客户端中填写了 API Key 才会发送该请求头，留空则不发送；是否校验由服务端决定 |

客户端默认等待响应 120 秒，超时视为失败。

## 2. 响应

响应体为 JSON，成功与失败使用同一结构：

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "8c7519cd63bc7346",
  "data": {
    "challenge": "5c1b6973e6a0d0d8291fbc5cb54f15d2",
    "validate": "e89d1b017f8d689efb36e890c23ea5bd"
  }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `code` | 是 | 整数，`0` 表示成功，非 `0` 表示失败。客户端仅以此判断成败 |
| `message` | 否 | 描述信息，失败时会写入日志 |
| `request_id` | 否 | 请求标识，返回时会一并写入日志，便于排查 |
| `data.validate` | 成功时必填 | 识别结果（极验 `validate`），必须非空 |
| `data.challenge` | 否 | 提交时使用的 `challenge`；缺省时使用请求中的 `challenge` |

- 失败时 `data` 可为 `null`。
- 其他多余字段会被忽略。
- 客户端只读取响应体，不依赖 HTTP 状态码，但响应体必须是 JSON。建议失败时返回对应的 4xx / 5xx。

失败示例：

```json
{ "code": 40101, "message": "invalid api key", "request_id": "034e6f585a0af740", "data": null }
```

## 3. 失败时的客户端行为

`code` 的取值由服务端自定，客户端只对下表中的值做特殊处理，其余非 `0` 的值一律视为失败，不重试：

| `code` | 含义（建议） | 客户端行为 |
|---|---|---|
| `42901` | 请求过于频繁 | 按响应头 `Retry-After`（秒，缺省 5）等待后重试；超过 60 秒则不再等待，直接失败 |
| `50301` | 服务繁忙 | 同上 |
| `50302` | 排队超时 | 同上 |
| `50001` | 上游暂时异常 | 间隔 1 秒后重试 |
| `50000` | 服务内部错误 | 间隔 1 秒后重试 |

- 单次识别最多请求 3 次。
- 无法识别时请直接返回非 `0` 的 `code`。客户端会重新获取新的验证码后再次调用，无需服务端处理重试。
